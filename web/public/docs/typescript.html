TypeScript

Write the SurrealQL you already know. surrealguard generate analyses it against your schema and types the result — no query builder, no cast, and nothing to wrap the string in.

@surrealguard/client @surrealguard/query @surrealguard/next @surrealguard/svelte 
import { db } from "./db";

// SurrealDB returns one result per statement, so `query` resolves the
// per-statement tuple. One statement, one element.
const [people] = await db.query("SELECT id, name, age, team FROM person");
//     ^? Array<{ age: number; id: RecordId<"person">; name: string; team: RecordId<"team"> }>

people[0].name.toUpperCase();      // string
people[0].nope;                      // ✗ Property 'nope' does not exist

That is the API. person.team is a RecordId<"team"> rather than a string, because that is what the SDK actually decodes and what a record link has to be on the wire. A query built at runtime is not in the registry and resolves to unknown[] — it still runs, and it is never any.

Setup

Three steps. Skipping any one of them yields any with no error on your own code, so none are optional — see when everything is any.

1. Install

@surrealguard/client is a real runtime dependency and the module the generated file augments by name. surrealdb is its peer. The CLI is a dev dependency.

$ npm install @surrealguard/client surrealdb
$ npm install -D surrealguard typescript

Add @surrealguard/svelte or @surrealguard/next only if you want the reactive helpers on this page; neither is needed for db.query.

2. Generate — with --out

Bare generate writes surrealguard.generated.ts to the workspace root, which is almost never where your imports point. Pass the path that matches how you import it, and put it in package.json so the path is written once:

Project--outImport as
Vanilla TSsrc/surrealguard.generated.ts./surrealguard.generated
SvelteKitsrc/lib/surrealguard.generated.ts$lib/surrealguard.generated
Next (with src/)src/surrealguard.generated.ts@/surrealguard.generated
Next (no src/)surrealguard.generated.ts@/surrealguard.generated
 
$ npx surrealguard generate --out src/surrealguard.generated.ts
generated src/surrealguard.generated.ts (4 queries, 11ms)

Commit the generated module — it is what makes a fresh checkout type-check with no build step. Re-run it whenever the schema or a query changes, or leave surrealguard watch running. See the CLI reference.

3. Create the client

// src/db.ts
import { createClient } from "./surrealguard.generated";

export const db = createClient({
  url: "ws://localhost:8000/rpc",
  namespace: "app",
  database: "app",
});

Import createClient from the generated file. That import is what loads the declare module augmentation; importing it from @surrealguard/client compiles fine and gives you unknown[] forever.

The connection opens lazily, on first use, so a module-level db is safe and no route has to remember to await db.connect(...). Import it anywhere — a component, a route handler, a plain module. There is nothing to provide, inject or wire up.

What generate emits

One file: a module augmentation keyed by each query's exact text, read by a single conditional generic. That is the whole mechanism.

import type { RecordId } from "@surrealguard/client";

export { createClient, defineQuery, defineLive, RecordId } from "@surrealguard/client";

declare module "@surrealguard/client" {
  interface SurqlRegistry {
    "SELECT id, name FROM person WHERE team = $team": {
      result: [Array<{ id: RecordId<"person">; name: string }>];
      params: { team: RecordId<"team"> };
    };
  }
}

Two rules keep it honest. There is no permissive string overload — a literal is also a string, so a fallback overload would rescue every mis-call into unknown. And a miss degrades to unknown, never any, which is asserted in the package's test-d/.

Params fall out of the same lookup: required exactly when the query reads them, forbidden when it does not.

const [red] = await db.query("SELECT id, name FROM person WHERE team = $team", {
  team: new RecordId("team", "red"),
});

await db.query("SELECT id, name FROM person WHERE team = $team");
// ✗ TS2554: Expected 2 arguments, but got 1.

await db.query("SELECT id, name FROM person WHERE team = $team", { team: "team:red" });
// ✗ TS2322: Type 'string' is not assignable to type '_RecordId<"team">'.

That last one is not pedantry. A RecordId parameter encodes to a record link on the wire (CBOR tag 8); a plain string encodes to a SurrealQL string, so WHERE team = $team matches with the class and returns nothing without it.

When everything is any

A type generator that silently produces any is worse than no type generator. There are exactly four ways to get there, and all four are silent on your code — the failure lands somewhere you would never look. If a result is any, it is one of these.
  1. @surrealguard/client is not installed. The generated file says declare module "@surrealguard/client". If that specifier does not resolve, TypeScript reports TS2664: Invalid module name in augmentation inside the generated file — which you would never open — and drops the entire registry. generate warns by name when it detects this.
  2. You imported from @surrealguard/client instead of the generated file. The augmentation loads with the import. Import createClient, defineQuery and RecordId from ./surrealguard.generated.
  3. The generated file is somewhere else. Bare generate writes to the workspace root. If your import points at src/lib/ and the file is at the root, you now have two of them and they will drift apart silently.
  4. A .svelte script has no lang="ts". Svelte does not typecheck an untyped script block at all — svelte-check reports zero errors on people[0].nope.definitely.not.a.field. Every Svelte snippet on this page says lang="ts" because copying the whole block is the point.

Naming a query, when a name earns its keep

defineQuery / defineLive infer the same string literal and read the same registry through the same conditional generic, so they buy no extra type safety. What they buy is a value.

// src/queries.ts — the one place these texts live
import { defineQuery, defineLive } from "./surrealguard.generated";

export const allPeople  = defineQuery("SELECT id, name, age, team FROM person");
export const peopleOf   = defineQuery("SELECT id, name FROM person WHERE team = $team");
export const livePeople = defineLive("SELECT id, name, age, team FROM person");

Reach for it when two places must agree on one query — an SSR preload and the component that subscribes to it. Write the text twice and they drift by a byte, the cache key stops matching, the seed is silently discarded and the page refetches: no error, no warning, no type failure. A value cannot drift. Also when you want the single-statement result unwrapped (db.run returns rows directly), or when something has to hold on to the query — db.watch, db.invalidate, a mutation's invalidates list.

const people = await db.run(allPeople);            // rows, no destructure
const red    = await db.run(peopleOf, { team });   // params checked

const stop = db.watch(livePeople, (rows) => render(rows));   // live, no other package

await db.invalidate(allPeople);                 // every binding of that query
await db.invalidate(peopleOf.with({ team }));   // just that binding

A query text the registry does not contain is a hard compile error on defineQuery, carrying its own remedy — for a literal, a miss means exactly one thing: the generated file is stale. That also catches the case nobody recognises as an edit, reformatting a query. defineQuery.unchecked("…") opts out and degrades to unknown[].

@surrealguard/svelte

Svelte 5 / SvelteKit. You may not need it — the typed client works in a component with nothing around it:

<script lang="ts">
  import { db } from "$lib/db";

  const rows = db.query("SELECT id, name, age, team FROM person");
</script>

{#await rows then [people]}
  <ul>{#each people as person (person.id)}<li>{person.name}</li>{/each}</ul>
{/await}

What the package adds is reactive state: a live query that re-renders as rows change, parameters that follow $derived state, and an SSR payload a component can pick up without naming the query twice.

<script lang="ts">
  import { createLive } from "@surrealguard/svelte";
  import { livePeople } from "$lib/queries";

  const people = createLive(livePeople);
</script>

{#each people.data as person (person.id)}
  <li>{person.name}</li>   // reconciled live: CREATE / UPDATE / DELETE by id
{/each}

Read people.data directly — no store $ prefix, because reading a getter tracks. It is always an array and starts [], so markup never needs ?? [].

setClient is not part of setup. db.query, db.run and db.watch work from a plain import { db } from "$lib/db" anywhere. setClient(db) in +layout.svelte exists for one thing: the reactive helpers (createQuery, createLive, createMutation) resolve their client from Svelte context so components do not thread db through props. Every one of them also accepts { client: db } directly — which is what a .svelte.ts module must do anyway, since setContext is only readable during component initialisation.

Reactive parameters go through a thunk. A function re-runs when its dependencies change, so the query re-subscribes; "skip" says "not yet" and keeps the row type. This is the rule @tanstack/svelte-query v6 and convex-svelte both arrived at.

const roster = createLive(() => slug ? liveTeam.with({ team }) : "skip");

For gap-free SSR, preload(db, livePeople) in a load returns a payload that carries its own key, text and params. The component passes it straight to createLive and subscribes to exactly the query the server ran, with the text appearing nowhere in the component.

@surrealguard/next

Next.js / React. You may not need it either — the default App Router pattern is the typed client on its own, with zero client JS:

// app/people/page.tsx  (Server Component)
import { getDb } from "@/lib/db.server";

export default async function Page() {
  const [people] = await getDb().query("SELECT id, name, age FROM person");
  return <ul>{people.map((p) => <li key={String(p.id)}>{p.name}</li>)}</ul>;
}
The server client must be per-request. Next imports the module into the server runtime, so a module-level client would share one connection, one auth session and one cache across every concurrent request and every user. Wrap it in React's cache(). A module-level client is correct in the browser, where there is one user and one session.

Anything passed to a client component must go through runJson: an RSC boundary accepts only plain values and offers no transport hook, so a RecordId instance crossing it throws "Only plain objects can be passed to Client Components". runJson gives you `person:${string}` and ISO strings.

The reactive part is hooks, backed by useSyncExternalStore. Provide the browser client once with <SurrealGuardProvider client={db}> (or pass { client } per hook), then:

"use client";
import { useLive } from "@surrealguard/next";
import { livePeople } from "@/lib/queries";

export function People() {
  const people = useLive(livePeople);
  return <ul>{people.data.map((p) => <li key={p.id}>{p.name}</li>)}</ul>;
}

No thunk here. A query reference carries a stable key, so the hook's memo dependency is [client, source.key] and React's "did my deps change" problem does not arise. The frameworks differ, so the APIs do.

preload(db, livePeople) from @surrealguard/next/server seeds a client component the same way SvelteKit's does; that entry carries no "use client" directive, so it is safe in an RSC.

@surrealguard/query

The framework-agnostic reactive core both adapters are built on. Reach for it directly only if you are writing your own binding, or want a cache without a framework — for one live subscription and nothing else, db.watch(livePeople, render) is simpler and needs no cache.

import { getQueryClient } from "@surrealguard/query";
import { db } from "./db";
import { livePeople } from "./queries";

const people = getQueryClient(db).observeLive(livePeople);
const stop = people.subscribe((state) => {
  if (state.status === "success") render(state.data);
});
  • Deduplicates. N subscribers to the same query share one cache entry, one LIVE SELECT and one reconciled array; the last unsubscribe issues one KILL.
  • Reconciles. A live query seeds from its underlying SELECT — a LIVE SELECT never replays existing records — then applies notifications by record id.
  • Caches by the query's own key (text plus stably serialised params, computed once on the reference), so an SSR seed and a client subscription cannot disagree about which entry they mean.
  • Bounds itself — entries drop gcTime after their last subscriber leaves, capped at maxEntries.

QueryState<T> is a discriminated union on status, so reading rows before checking the status is a type error rather than a silently empty array.

Values are the SDK's values

The SDK decodes SurrealQL values as its own classes, so that is what the generated types say: record<team> → RecordId<"team">, datetime → Date (because createClient sets codecOptions.useNativeDates), duration → Duration, uuid → Uuid, decimal → Decimal.

Class instances do not survive SvelteKit's load (devalue) or a React Server Component's props. Json<T> is the projection that does — it is the SDK's own Jsonify, so the mapping is theirs: RecordId<"person"> becomes `person:${string}` and Date becomes string. db.runJson, preload and the whole reactive layer are Json<T>-shaped for this reason; db.query and db.run are not.

That asymmetry is deliberate rather than an oversight: uniformity in the other direction would either break SSR or break Next entirely, since an RSC boundary rejects class instances and has no transport hook to widen. If you want SDK-class fidelity through a SvelteKit load, @surrealguard/svelte/transport is a ready transport hook.
