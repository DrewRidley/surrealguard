CLI

The surrealql-analyzer binary analyzes a workspace of .surql sources and reports findings as text or JSON. It has four subcommands: init, check, generate, and watch.

surrealql-analyzer init surrealql-analyzer check [--json] surrealql-analyzer generate [--out <path>] surrealql-analyzer watch [--out <path>]

init

Writes a starter surrealql-analyzer.toml in the current directory. If one already exists, it is left untouched.

$ surrealql-analyzer init
created surrealql-analyzer.toml
next: point [sources] at your .surql files, then run `surrealql-analyzer check`

check

Discovers every .surql/.surrealql file under the workspace root (the nearest ancestor directory containing surrealql-analyzer.toml), analyzes them in sorted path order against the schema they define, and reports findings. Severity is resolved through the workspace policy — warnings_as_errors promotion and [lints] levels (named lints, specific codes like E1002, and family wildcards like "7xxx") apply here, at the consumption edge.

$ surrealql-analyzer check
error[E1002]: unknown field `team` on table `user`
  --> queries/users.surql:1:37
  |
1 | SELECT name, age FROM user WHERE team = $team;
  |                                  ^^^^
  |
  = help: did you mean `age`?

checked 2 sources in 6ms
found 1 error

Colour

On a terminal the severity word, the diagnostic code, file paths, the scaffold and the caret underline are coloured — a related note: is underlined in the scaffold's colour rather than the severity's, so it can never be mistaken for the finding itself. Everywhere else the output is the same text with no escape sequences, which is what makes surrealql-analyzer check > report.txt and a CI log readable. Colour is off whenever any of these hold:

ConditionWhy
--no-colorExplicit opt-out; accepted on every subcommand.
NO_COLOR set to anything non-emptyThe no-color.org convention.
TERM=dumbThe terminal cannot render escapes.
The destination is not a TTYA pipe, a file, a CI log. Decided per stream, so check > out.txt writes plain text to the file while errors on the terminal keep their colour.

--json never gets colour or a progress spinner under any condition: it is a machine contract, and one document with one exit code is all it emits.

--json

Emits machine-readable diagnostics instead of the text renderer. The document has two top-level keys, summary and diagnostics:

{
  "summary": {
    "sources_checked": 2,
    "diagnostics": 1,
    "errors": 1
  },
  "diagnostics": [
    {
      "code": "E1002",
      "severity": "error",
      "source": "queries/users.surql",
      "range": { "start": 41, "end": 45 },
      "message": "unknown field `team` on table `user`",
      "help": ["did you mean `name`?"],
      "related": [
        {
          "source": "schema/user.surql",
          "range": { "start": 0, "end": 26 },
          "message": "table `user` defined here"
        }
      ]
    }
  ]
}
FieldTypeNotes
summary.sources_checkednumberCount of analyzed sources.
summary.diagnosticsnumberFindings that survived policy (errors + warnings + hints).
summary.errorsnumberError-severity findings; non-zero fails the check.
codestringSeverity-prefixed code — E error, W warning, I hint, S syntax (e.g. E1002, W4022, I7007, S0001). The prefix reflects the resolved severity, so a promoted warning renders as E….
severitystring"error", "warning", or "hint".
sourcestringThe source path/id the span belongs to.
range{ start, end }Byte offsets into that source — precise enough for surgical inline edits.
messagestringThe finding message.
helpstring[]Zero or more help lines.
relatedobject[]Related spans, each { source, range, message } — e.g. where a table was defined.
On a clean run the diagnostics array is empty and only the summary is populated; the diagnostics array is filled when the check fails. The help and related arrays are always present, often empty.

generate

Scans host-language files for embedded SurrealQL, analyzes each query against the workspace schema, and writes a TypeScript module that re-exports the runtime entry points (createClient, defineQuery, defineLive, the SDK value classes) and augments the query registry. Host files are discovered by extension — .ts, .tsx, .js, .jsx, .svelte, .vue, .astro — honoring the same ignore patterns as .surql discovery.

# the file re-exports a runtime value, so write it to a .ts
$ surrealql-analyzer generate --out src/surrealql-analyzer.generated.ts
generated src/surrealql-analyzer.generated.ts (4 queries, 11ms)

The emitted file both re-exports createClient and augments @surrealdb/analyzer-client. Import the client from that one file — that also loads the augmentation, so every db.query("…") resolves the result and params of each analyzed query from its exact text, with no separate side-import. Pass an --out that matches how you import it: the default is the workspace root, which is rarely where $lib/ or @/ points, and a mismatch leaves two generated files that drift apart in silence. See the TypeScript page.

@surrealdb/analyzer-client must be installed for that augmentation to mean anything. A declare module whose target does not resolve is not an augmentation — TypeScript reports TS2664 inside the generated file, drops the whole registry, and every query in your own code silently becomes any with no error on it. generate checks the package resolves from the output's own directory and warns by name when it does not: 
warning: `@surrealdb/analyzer-client` is not installed
  --> src/surrealql-analyzer.generated.ts
  |
  | this file augments `declare module "@surrealdb/analyzer-client"`, and an
  | augmentation whose target does not resolve is silently dropped —
  | TypeScript reports TS2664 here, and every query typed through it
  | degrades to `any` with no error on it.
  |
  = help: npm install @surrealdb/analyzer-client surrealdb

watch

The development loop, to run beside your dev server. On every change to a .surql source, a host file, or surrealql-analyzer.toml it runs the full check, and regenerates the registry when — and only when — that check passes.

$ surrealql-analyzer watch --out src/surrealql-analyzer.generated.ts
surrealql-analyzer watch /home/you/app
run 2 · schema/person.surql changed · 6ms

PASS 4 sources · no diagnostics · wrote src/surrealql-analyzer.generated.ts (3 queries)

watching .surql, host files and surrealql-analyzer.toml — Ctrl-C to stop

Pairing the two verbs is the point: check alone leaves the generated types stale, and generate alone reports only the queries it embeds, so a broken .surql file passes unmentioned. Generating second, and only on a clean check, means a half-typed save never overwrites a registry that worked.

Each run repaints the screen rather than scrolling the last one away — a watch is a display of the workspace's current state, not a log of its history — and ends in a PASS / WARN / FAIL band. Piped output cannot be cleared, so runs are separated by a rule instead. --check-only writes nothing, which is the mode for a workspace whose registry is committed and reviewed. check --watch and generate --watch still watch a single verb each.

Exit codes

CodeMeaning
0Success — no error-severity findings survived policy (warnings and hints do not fail the check unless warnings_as_errors promotes them).
1The check found one or more error-severity findings, or a command failed (missing/invalid config, unreadable source, I/O error).

In JSON mode the process still exits 1 on a failing check, but the diagnostics are printed to stdout as JSON rather than to stderr as text — so a wrapper can parse findings on failure and read the exit code as a pass/fail signal.
